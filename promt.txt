# 6. SUPPORTED DIRECTIVES

The only valid directive types are:

1. `solar_reduction`
2. `minimum_battery_reserve`
3. `no_charge_window`
4. `no_discharge_window`
5. `max_grid_window`
6. `no_op`

No other directive type is allowed.

## solar_reduction

Meaning:

Reduce usable solar during specified hours.

Schema:

```json
{
  "hours": [13, 14],
  "factor": 0.2
}
```

Important:

`factor` is the fraction of solar remaining.

For example:

* 100% remaining → `1.0`
* 80% remaining → `0.8`
* 50% reduction → `0.5`
* 80% reduction → `0.2`
* 20% remaining → `0.2`

Never confuse percentage reduction with remaining fraction.

Constraint:

```text
0 <= factor <= 1
```

Effective solar:

```text
effective_solar[h] = original_solar[h] * factor
```

for every affected hour.

## minimum_battery_reserve

Schema:

```json
{
  "hours": [18, 19, 20],
  "minimum_energy_kwh": 120
}
```

During affected hours:

```text
battery_energy_after[h]
    >= max(base_minimum_energy, directive_minimum_energy)
```

The reserve value must be:

* finite
* non-negative
* no greater than battery capacity

## no_charge_window

Schema:

```json
{
  "hours": [14, 15]
}
```

During these hours:

```text
battery_charge = 0
```

## no_discharge_window

Schema:

```json
{
  "hours": [18, 19, 20]
}
```

During these hours:

```text
battery_discharge = 0
```

## max_grid_window

Schema:

```json
{
  "hours": [17, 18],
  "max_grid_kwh": 100
}
```

During these hours:

```text
grid_kwh <= max_grid_kwh
```

The grid cap must be finite and non-negative.

## no_op

For notes irrelevant to the current 24-hour energy schedule:

```json
{
  "applies": false,
  "directive_type": "no_op",
  "structured_adjustment": null
}
```

All other directive types must have:

```text
applies = true
```

# 7. TIME INTERPRETATION

Use whole-hour semantics.

The start is inclusive.

The end is exclusive.

Examples:

"1 PM to 3 PM"

means:

```text
[13, 14]
```

not:

```text
[13, 14, 15]
```

"2 AM until 5 AM"

means:

```text
[2, 3, 4]
```

"13:00-15:00"

means:

```text
[13, 14]
```

The LLM must interpret natural-language time expressions into explicit integer hours.

The deterministic guardrail must verify:

* integer type
* 0 <= hour <= 23
* uniqueness
* ascending ordering

Do not permit duplicated hours.

# 8. LLM INTERPRETATION DESIGN

Make a single LLM call for all operator notes whenever possible.

Do not make three independent model calls for three notes unless there is a strong reason.

The LLM should receive:

* the operator notes
* the 24-hour planning-horizon definition
* the supported directive ontology
* precise interpretation rules
* output schema
* important examples
* explicit instruction that unrelated operational/business notes must become `no_op`

The LLM should NOT be asked to solve the energy optimization.

Its responsibility is semantic interpretation only.

The LLM output should look like:

```json
{
  "directive_interpretation": [
    {
      "note_index": 0,
      "applies": true,
      "directive_type": "solar_reduction",
      "structured_adjustment": {
        "hours": [13, 14],
        "factor": 0.2
      },
      "explanation": "Solar availability is reduced during the stated maintenance window."
    }
  ]
}
```

The model should return one item per input note.

No missing notes.

No duplicate mappings.

Correct `note_index` ordering.

# 13. OPTIMIZATION MODEL

Create a mathematical optimization model for 24 hours.

For each hour h define:

```text
grid[h] >= 0
solar_used[h] >= 0
charge[h] >= 0
discharge[h] >= 0
energy[h] >= 0
```

Also enforce mutually exclusive battery actions.

Use binary variables or an equivalent exact formulation so that the returned schedule cannot simultaneously charge and discharge the battery in the same hour.

Use:

```text
charge[h] <= max_charge_per_hour * charge_mode[h]

discharge[h] <= max_discharge_per_hour * discharge_mode[h]

charge_mode[h] + discharge_mode[h] <= 1
```

where appropriate.

# 14. ENERGY BALANCE

Every hour must satisfy exactly:

```text
grid_kwh
+ solar_used_kwh
+ battery_discharge_kwh
=
demand_kwh
+ battery_charge_kwh
```

Do not allow energy creation or disappearance.

Do not allow negative grid energy.

Do not allow grid export.

Unused solar is curtailed.

# 15. SOLAR CONSTRAINT

For each hour:

```text
0 <= solar_used[h] <= effective_solar[h]
```

where:

```text
effective_solar[h]
=
original_solar[h]
```

unless a `solar_reduction` directive affects that hour.

For affected hours:

```text
effective_solar[h]
=
original_solar[h] * factor
```

Do not allow solar use above the reduced amount.

# 16. BATTERY STATE TRANSITION

For each hour:

If charging:

```text
E_after = E_before + charge
```

If discharging:

```text
E_after = E_before - discharge
```

If idle:

```text
E_after = E_before
```

For idle:

```text
battery_kwh = 0
```

The optimizer must preserve the battery state across all 24 hours.

# 17. BATTERY BOUNDS

For every hour:

```text
minimum_energy_kwh <= battery_energy_after <= capacity_kwh
```

If a `minimum_battery_reserve` directive is active:

```text
battery_energy_after
>= max(base_minimum_energy, directive_reserve)
```

Charge must obey:

```text
charge <= max_charge_kwh_per_hour
```

Discharge must obey:

```text
discharge <= max_discharge_kwh_per_hour
```

# 18. END-OF-DAY NEUTRALITY

At hour 23:

```text
battery_energy_after[23]
=
initial_energy_kwh
```

Do not let the optimizer exploit the starting battery as free energy.

This is mandatory.

# 19. GRID CAP

For an active `max_grid_window`:

```text
grid[h] <= max_grid_kwh
```

for every affected hour.

This must be a hard optimization constraint.

Do not merely mention the constraint in `plan_summary`.

# 20. NO-CHARGE / NO-DISCHARGE

For `no_charge_window`:

```text
charge[h] = 0
```

For `no_discharge_window`:

```text
discharge[h] = 0
```

Do not rely on the solver naturally choosing zero; explicitly constrain it.

# 21. OBJECTIVE

After all directives have been applied, minimize:

```text
total_cost_bdt
=
sum(
    grid_kwh[h] * tariff_bdt_per_kwh[h]
)
```

for h = 0..23.

The optimizer should optimize grid electricity cost, not merely grid energy.

A higher-tariff hour should generally be avoided when another feasible source is available, but let the mathematical model determine the actual schedule.

Do not implement a greedy "use battery during expensive hours" heuristic as the primary solver.

Use a real optimization model.

# 22. IMPORTANT OPTIMIZATION EDGE CASE

Do not accidentally create artificial arbitrage from simultaneous charging and discharging.

The model must prevent both actions from being positive in the same hour.

Use exact solver constraints rather than a fragile post-processing fix.

If the optimization result is numerically imperfect, validate and normalize it using a very small tolerance, then replay it.

Never modify a schedule in post-processing in a way that changes its feasibility without revalidation.

# 28. FLOATING-POINT HANDLING

Use floating-point tolerances carefully.

The challenge uses approximately 0.01 kWh / 0.01 BDT tolerance.

Internally:

* use reasonable numerical precision
* avoid repeated rounding
* use a central tolerance constant
* validate using absolute tolerance

Do not round every intermediate computation.

Round only when producing the final external JSON.

After final rounding, replay the rounded schedule again.

If rounding causes a violation, correct the representation and revalidate rather than returning invalid output.

Never return `-0.0`.

Normalize tiny values to `0.0`.
